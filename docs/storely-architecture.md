# Storely CMS — ארכיטקטורה

קוד הליבה של Storely נכתב פעם אחת. כל לקוח מקבל אתר Next.js עצמאי, עם דומיין משלו ועם ממשק ניהול ב־`/admin`. כל האתרים מתחברים לפרויקט Supabase מרכזי אחד. ההפרדה בין חנויות היא `store_id` ומדיניות RLS, לא מסד נפרד.

המודל הקודם, שבו לכל חנות היה פרויקט Supabase משלה, הוחלף. פירוט החיבור, המשתמשים, המודולים והאבטחה נמצא ב־[ארכיטקטורת Multi-Tenant](multi-tenant-architecture.md). מבנה הטבלאות נמצא ב־[תכנון הסכמה](database-schema-plan.md).

המסמך הזה מתאר את גבולות הקוד. הוא אינו מחבר Supabase ואינו משנה את העיצוב.

## מה קיים בקוד עכשיו

| תיקייה | תפקיד בהמשך |
| --- | --- |
| `src/platform` | `storely-core`: הרשאות, הקשר חנות, מודולים, נקודות הרחבה |
| `src/platform/data-access.ts` | שכבת הגישה לנתונים. כל שאילתה תקבל `StoreScope` מהסשן המאומת |
| `src/platform/platform-access.ts` | הרשאות בעל הפלטפורמה, בנפרד מחברות בחנות |
| `src/components/admin`, `src/app/admin` | `storely-admin` |
| `src/modules` | `storely-modules`, הקטלוג המשותף |
| `src/store` | תצורת הפריסה הזו: לאיזו חנות האתר משויך, ואילו מודולים כבויים אצלה עד חיבור המסד |
| עדיין אין | `storely-storefront` |
| עדיין אין | פאנל הפלטפורמה |

`src/store/installation.ts` קושר את אתר הפיתוח לחנות `lavana` בסביבת `development`. זהו מקור שרת. הוא אינו נקרא מהדפדפן, והוא אינו פרויקט Supabase נפרד. מערך `modules` מחליף זמנית את שורות `store_modules` של החנות הזו.

העיצוב המאושר נשאר כפי שהוא. מודול הדוגמה וכרטיס ההרחבה כבויים, ולכן התפריט והדשבורד אינם משתנים.

## השכבות

```text
Core                  לוגיקה משותפת. מתעדכנת במרכז ומופצת לאתרי החנויות.
Admin UI              מעטפת הניהול. מודול משתמש ברכיבים ובטוקנים הקיימים.
Storefront SDK        קריאות האתר הפונה ללקוח. עדיין לא נבנה.
Modules               תוספות מהקטלוג. חנות מפעילה מודול בשורה משלה.
Store configuration   שיוך האתר לחנות, והרחבות קוד של החנות הזו.
Database access       שאילתה רצה רק עם מזהה חנות שהשרת אימת.
Auth and permissions  זהות אחת, חברות לכל חנות בנפרד, הרשאה לכל פעולה בנפרד.
```

שינוי עבור לקוח אחד נכתב כהרחבת חנות או כשורת תצורה של אותה חנות. הוא אינו נכתב כתנאי על מזהה חנות בתוך הליבה.

## משתמשים, בקצרה

בשלב העיצוב `getAdminSession()` מחזירה את מאיה ברק כבעלת חנות לבנה בלבד. אין התחברות ואין הרשמה.

כשהמסד יחובר, Supabase Auth המרכזי מזהה את האדם. `store_members` קובע לאילו חנויות הוא שייך. `role_permissions` קובע מה מותר לו בכל חנות. בעל הפלטפורמה נבדק בטבלה נפרדת, לא דרך תפקיד בחנות.

ההרשאה נבדקת מול מזהה החנות של הסשן. מזהה שמגיע מהדפדפן אינו מחליף אותו.

## מודולים

מודול הוא אובייקט `StorelyModule`: מזהה, שם, גרסה, הרשאות, פריטי ניווט, תרומות לנקודות הרחבה, ומיגרציות. הקטלוג הוא `src/modules/catalog.ts`. הופעה בקטלוג של פריסה אחת אינה מפעילה את המודול בחנות, ואינה מחייבת פריסה אחרת לכלול את אותו קוד.

| מצב בחנות | משמעות |
| --- | --- |
| אין שורה ב־`store_modules` | המודול לא מותקן בחנות הזו |
| השורה קיימת ו־`enabled` כבוי | הנתונים יכולים להישאר. התפריט, המסך וה־API סגורים |
| השורה קיימת והמודול פעיל, ויש הרשאה | הפריט מופיע והפעולות נפתחות |

`moduleAccess(session, id)` מחזיר `ok`, או `not_installed`, `disabled`, `forbidden`. כיבוי בחנות אחת אינו משנה חנות אחרת.

`loyalty-program` מותקן עבור לבנה וכבוי. `wholesale-orders` נמצא בקטלוג ואין לו שורה בחנות הזו. הפעלה היא `enabled: true` ברשומה של החנות, ואחר כך ב־`store_modules`.

## נקודות הרחבה

| נקודה | שימוש |
| --- | --- |
| `dashboard.cards` | כרטיס בדשבורד |
| `product.tabs` | לשונית במוצר |
| `order.actions` | פעולה בהזמנה |
| `customer.sections` | אזור בפרופיל לקוח |
| `settings.sections` | מקטע בהגדרות |
| `navigation` | עמוד בתפריט, כשדה על המודול |

`contributions(session, point)` מחזיר רק פריטים של מודול פעיל בחנות של הסשן, ורק אם יש הרשאה. רשימה ריקה אינה מוסיפה רכיב למסך.

`src/store/extensions/lavana-studio-note.ts` הוא כרטיס של חנות אחת. הוא כבוי, והוא אינו חלק מהקטלוג המשותף.

## מה מחוץ לשלב הזה

- אין חיבור Supabase, אין קבצי מיגרציה, ואין טבלאות.
- אין מסך התחברות ואין פאנל פלטפורמה.
- אין שינוי בתפריט או בדשבורד כל עוד דגלי המודולים כבויים.

סדר החיבור למסד, אחרי סיום המרת העיצוב, כתוב בסוף מסמך ה־Multi-Tenant.
